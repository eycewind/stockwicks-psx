# C1 Delivery: Application Discovery and Local Runtime Plan

## 1. Executive Summary

The inherited repository is a server-rendered FastAPI application with a PostgreSQL
database and Celery/Redis background processing. Its production topology is:

- FastAPI/Uvicorn web process (`app.main:app`)
- Celery worker (`app.celery_worker.celery`)
- Celery Beat scheduler (`app.celery_worker.celery`)
- PostgreSQL application database
- Redis broker/result backend and runtime flags
- Local `data/`, `logs/`, and `models/` storage
- An optional standalone Sparkie weekly scheduler

The portal can be brought up in a reduced local mode with the web process and
PostgreSQL. Redis, the worker, and Beat are needed for asynchronous/scheduled bot
execution, but not for static portal inspection or a manually invoked historical
daily strategy test. Live trading must remain disabled.

The stock bot's primary market-data dependency is Schwab
`GET /marketdata/v1/pricehistory`. It consumes millisecond timestamps and OHLCV
candles. Live/risk functions also use `GET /marketdata/v1/quotes`. The price-history
URL is hardcoded in production stock modules; unlike the trader base URL, it has no
general configuration seam. This is the first application change needed in a later
integration contract.

The adjacent PSX database was verified at
`/home/hassan/psx-stock-watcher/data/psx_watcher.db`. Its `daily_ohlc` table has
621,794 rows, 821 symbols, and dates from 2020-01-01 through 2026-07-10. It contains
raw and adjusted daily OHLCV fields. It does **not** contain intraday candles.
Consequently:

- Daily historical stock evaluation is supportable.
- Minute strategies, current quotes, options, SPX 0DTE, extended-hours logic, and
  live order handling are not supportable from this dataset.
- Daily candles must not be returned in response to minute-frequency requests.

The smallest safe target is a development-only, paper-trading runtime with FastAPI,
PostgreSQL, an explicit local PSX compatibility API, and optional Redis/Celery when
scheduled execution is required. A later contract should add pinned dependency
metadata and a development Compose file. There is currently no dependency manifest
or application Docker/Compose definition in this repository, so a reproducible
runtime cannot yet be built from source alone.

No source application files, services, dependencies, databases, or migrations were
changed or executed during C1. Only this document was created.

## 5. Authentication and Configuration Findings

- Market-token acquisition is file based in legacy stock utilities. Celery's
  `auto_refresh_user_token` discovers numeric user directories containing
  `schwab_market_token.json` or `schwab_trade_token.json`.
- The Beat schedule refreshes market and trade tokens every ten minutes. Refresh
  utilities use the OAuth token endpoint, refresh-token grant, expiry safety
  windows, retry/backoff files, and environment-provided client credentials.
- Broker routes also persist connection/account metadata in PostgreSQL.
- The local PSX compatibility API should default to loopback-only access and require
  no Schwab token. The application adapter may omit Authorization locally or send
  an ignored placeholder. It must never reuse a real Schwab credential.
- `SCHWAB_TRADER_BASE` is configurable for trade calls. Selected option scripts
  honor `SCHWAB_API_URL`. Stock `BASE_URL` constants in
  `schwab_price_history.py`, `data_fetch.py`, and related scripts are hardcoded.
- A later integration contract should introduce one explicit setting such as
  `MARKET_DATA_BASE_URL` and one provider mode such as
  `MARKET_DATA_PROVIDER=schwab|psx_local`. It should not redirect trader/OAuth
  traffic to the compatibility service.
- The repository contains unsafe development defaults and legacy fallback
  connection strings. No default secret value is reproduced here. The local
  runtime must require newly generated sanitized credentials.

## 6. US-Market Assumptions

| Assumption/evidence | Classification | PSX treatment |
|---|---|---|
| `US/Eastern`/`America/New_York` in price history, tasks, Beat, backtests, and trading-window utilities | Requires code change | Use `Asia/Karachi` or trade-date semantics for PSX |
| Equity session 09:30–15:55/16:00 ET in `stock_tasks.py` and data helpers | Requires configuration/code change | Disable for historical daily mode; define PSX session only for future live work |
| Beat daily tick at 16:10 ET and EOD close at 15:58 ET | Requires configuration | Do not enable Beat with these schedules for PSX |
| Weekend-only checks and manually embedded NYSE holidays | Requires code change/further investigation | Use PSX trading calendar derived from data and an authoritative holiday source |
| Premarket/after-hours flags; intraday helpers default to extended hours | Unsupported by daily dataset | Reject minute/extended-hours requests |
| Minute intervals 1/5/10/15/30 and staleness thresholds | Unsupported by daily dataset | Only `frequencyType=daily`, `frequency=1` initially |
| Timestamp conversion from epoch UTC to Eastern | Requires code change | Encode each PSX daily candle at a documented stable instant; never convert it through ET to derive trade date |
| US tickers, `$SPX`, `SPXW`, QQQ/SPY, OCC option symbols, slash-prefixed futures | Requires code change/unsupported | Initial service accepts exact PSX DB symbols only; no exchange suffix guessing |
| Dollar display/position math and price rounding (often 2–4 decimals) | Requires configuration | Label PKR and preserve DB numeric precision; PSX tick-size rules need further investigation |
| `lastPrice` live quote behavior | Unsupported by daily dataset | Do not claim latest daily close is a live quote |
| Previous-close flag | Requires configuration | Daily endpoint may calculate prior available close only if the application demonstrably consumes it |
| Adjusted versus unadjusted OHLC | Requires explicit choice | DB contains both. Initial compatibility response should default to raw OHLCV for Schwab-like semantics and offer an explicit local-only adjusted mode if needed |
| Thin-stock/zero-volume assumptions | Requires code change | Preserve real PSX liquidity. DB notes indicate missing opens and official closes can have PSX-specific behavior |
| Long and short strategies | Requires code change | Initial validation should be long-only unless PSX short-sale eligibility is separately modeled |
| Fractional quantities | Requires code change/further investigation | Use whole-share quantities for PSX testing |
| US market/limit/option orders and settlement | Unsupported/further investigation | No live order API in initial scope |
| Commission/slippage defaults, sometimes zero or US-style fixed values | Requires code change | Use the PSX watcher's PKR costs/taxes model and liquidity-aware slippage |
| Corporate actions | Requires configuration | Prefer adjusted series for total-return research only when the strategy contract specifies it; never mix raw and adjusted fields |

### Timestamp requirement

`trade_date` is authoritative in the PSX SQLite database. The compatibility API
must produce a millisecond epoch that round-trips to the same PSX calendar date.
A safe initial rule is **00:00:00 Asia/Karachi on `trade_date`, converted to UTC
epoch milliseconds**, while clients must derive daily labels in Asia/Karachi or
from a separate documented trade-date field. Existing code converts to Eastern,
which would display the previous date for many such timestamps. Therefore the
application's DataFrame conversion must also change; choosing another artificial
hour in the API alone would hide rather than fix the bug.

## 7. Minimum PSX Compatibility API Specification

### Required endpoint

`GET /marketdata/v1/pricehistory`

| Item | Initial contract |
|---|---|
| Supported parameters | `symbol` required; `frequencyType=daily`; `frequency=1`; optional inclusive `startDate`/`endDate` as Unix epoch milliseconds; alternatively `periodType`/`period` only for combinations explicitly mapped to a daily date window; `needExtendedHoursData=false`; `needPreviousClose=false` initially |
| Response | JSON object with `symbol`, `empty`, and `candles`; each candle contains integer `datetime`, numeric `open`, `high`, `low`, `close`, and integer `volume` |
| Order | Ascending `datetime`, one candle per `(trade_date, symbol)` |
| Source mapping | Default raw `open/high/low/close/volume` from `daily_ohlc`; rows with missing required values need a documented policy. Do not fabricate OHLC |
| Timestamp | Unix milliseconds for 00:00 Asia/Karachi on `trade_date`; application must retain PSX date semantics |
| No results | HTTP 200 with `empty: true` and `candles: []` |
| Invalid symbol | HTTP 404 with stable error JSON; symbols normalized only by trim/uppercase, not suffix translation |
| Unsupported frequency | HTTP 422 (or 400 if exact Schwab compatibility requires it) with a stable `UNSUPPORTED_FREQUENCY` error; never return daily bars |
| Extended hours | `true` rejected as unsupported |
| Authentication | None for loopback/private development; reject non-loopback exposure by deployment policy |
| Database access | SQLite URI/read-only connection; parameterized SQL; bounded date window and response size |

The existing application sends either date bounds or `periodType`/`period`.
Supporting date bounds is mandatory. Period mappings should be limited to the
combinations reached by the selected daily workflow; unsupported combinations
must fail explicitly.

### Optional endpoint

`GET /marketdata/v1/quotes` is optional and not required for offline historical
signal generation. If later implemented, it must identify the value as an EOD
close with its trade date, not as a real-time `lastPrice`. Existing worker P&L
logic expects live quotes, so it should remain disabled rather than silently use
stale closes.

OAuth, accounts, orders, option chains, instruments, market hours, and streaming
are explicitly outside the initial compatibility service. The current PSX database
cannot honestly support them.

## 8. Recommended Local Runtime

### Selected approach

Create a **development-only Compose topology in the next contract**, containing:

1. `web` (FastAPI/Uvicorn)
2. `postgres`
3. `psx-api` with the SQLite database mounted read-only
4. Optional `redis` and `worker` profiles
5. Beat excluded by default

This is the smallest reproducible approach that isolates the inherited
application's PostgreSQL/Redis requirements, preserves logs/test outputs in named
volumes, and gives the PSX API a stable internal hostname. It avoids installing
systemd/nginx or modifying host services.

### Viable-option comparison

| Option | Evidence/benefit | Limitation | Decision |
|---|---|---|---|
| Existing Docker/Compose | None in this application repository | Not available | Rejected |
| New development Compose | Cleanly expresses web/Postgres/PSX API and optional Redis/Celery; supports read-only SQLite mount | Requires dependency lock recovery and new dev files | **Recommended** |
| Native virtualenv plus host services | Setup scripts demonstrate Uvicorn/Celery commands | No dependency manifest; risks host drift; PostgreSQL/Redis setup is less isolated | Useful diagnostic fallback, not the primary recommendation |

### Reduced-mode stages

- Stage A: PSX API contract tests against the read-only SQLite DB.
- Stage B: Web + PostgreSQL, trading disabled, no Celery. Verify `/healthz`,
  authentication, and relevant portal screens.
- Stage C: Manually invoke one known daily stock algorithm against the local API
  with fixed dates and capture logs/results.
- Stage D: Add Redis + worker if UI submission requires Celery.
- Stage E: Add a PSX-aware daily schedule only after timezone/calendar work. Do not
  enable the inherited Beat schedule unchanged.

Required sanitized settings include local database/Redis URLs, generated app/JWT
secrets, local data/log/model paths, `TRADING_ENABLED=false`,
`LIVE_TRADING_ENABLED=false`, `PAPER_TRADING_ENABLED=true`,
`EMERGENCY_STOP=true` until validation, and the future market-data provider/base
URL settings. No Schwab client secret or token is required for local PSX history.

## 9. Missing Inputs and Blockers

1. No dependency manifest or lock file exists, blocking a reproducible Python
   environment.
2. No application Dockerfile/Compose definition exists.
3. The exact "friend's signal-generation workflow" entry point, algorithm,
   interval, symbol universe, and expected output have not been identified.
4. Price-history URLs are duplicated/hardcoded; a provider configuration seam is
   required.
5. The daily strategy path must be traced through the selected algorithm because
   many bot paths fetch minute data even when a `1d` interval is configured.
6. PostgreSQL schema provisioning is not versioned. Production setup clones a
   schema from another database, and startup code performs ad-hoc table creation.
7. Preserved `models/` artifacts are absent from the repository.
8. Current working tree contains substantial pre-existing deleted/untracked files
   and temporary clones. They were not modified. The intended authoritative source
   state should be confirmed before later implementation.
9. PSX trading calendar, tick sizes, short-sale rules, fees/taxes, and settlement
   rules require an authoritative product decision before trading simulation.
10. The PSX DB currently ends at 2026-07-10; freshness expectations must be defined.

## 10. Risks and Open Questions

- Importing `app.main` may have schema-creation side effects; C1 therefore did not
  perform an import smoke test.
- Web startup mounts `DATA_DIR` with `check_dir=True`; a missing directory can
  prevent startup.
- Celery Beat would immediately schedule intraday US-market work and token refresh.
- Legacy modules duplicate API calls, timezone conversions, and error handling.
  Patching only the primary helper could leave silent Schwab traffic elsewhere.
- Some HTTP paths return raw upstream JSON without `raise_for_status`, while others
  swallow errors and return empty DataFrames. Contract tests must standardize the
  boundary used by the selected workflow.
- The PSX database has `open_missing` and adjusted fields. The strategy must define
  whether missing-open days are excluded and whether raw or adjusted candles are
  required.
- PSX notes indicate an official close can differ from the intraday range for thin
  stocks. Generic US OHLC invariants may reject valid rows.
- The web app mixes portal, broker, live-trading, options, research, and commercial
  administration features. Reduced mode needs feature flags or disciplined route
  selection.
- It is an inference, not yet verified, that all relevant UI pages can render
  without Redis and external provider calls. This must be tested after dependencies
  and a disposable PostgreSQL schema are available.
